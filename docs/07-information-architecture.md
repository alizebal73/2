# معماری نهایی اطلاعات و جای قابلیت‌ها

این سند قرارداد نهایی Information Architecture پروژه است. Prototypeهای موجود همچنان مرجع UI و رفتار هستند؛ این سند فقط مشخص می‌کند هر قابلیت در کدام محل محصول قرار بگیرد.

## اصل اصلی
اپراتور باید بیشتر عملیات روزمره را از داشبورد و کارت ایستگاه انجام دهد. صفحات مدیریتی برای تنظیمات، داده‌های مرجع، گزارش و کارهای کم‌تکرار هستند.

## مالکیت قابلیت‌ها

صفحه مستقل «مدیریت» نباید به مقصد اصلی UI تبدیل شود.

## قرارداد تکمیلی Dashboard / Reports / Staff / Inventory

### Dashboard
کارت ایستگاه در نمای عادی باید وضعیت عملیاتی و مشتری را در اولویت نشان دهد:
نام/شماره دستگاه، username مشتری، نام کامل، زمان باقی‌مانده معتبر، بدهی، یادداشت کوتاه و وضعیت دستگاه. قیمت ساعتی در کارت اصلی نمایش داده نمی‌شود و در Start/Session Center/Settlement دیده می‌شود.

PCها باید Group By و فیلتر بر اساس وضعیت، VIP/عادی، اینترنت ۱/۲ و بازه زمان باقی‌مانده داشته باشند. یک Group By اصلی و فیلترهای مکمل استفاده می‌شود.

### Reports
گزارش‌ها در یک Report Center دسته‌بندی می‌شوند: مالی، جلسات/ایستگاه‌ها، مشتری/VIP، بوفه/موجودی، کاربران/شیفت و Audit. بازه زمانی یک کنترل مشترک است و Detail هر گزارش در پنل/زیرصفحه خودش نمایش داده می‌شود.

### Users & Shift
این بخش علاوه بر User/Permission مالک حضور و شیفت، تسویه صندوق، تحویل شیفت، پروفایل حقوقی پرسنل، پرداخت حقوق، پاداش/کسری/مساعده و حساب طلب/بدهی پرسنل است.

### Buffet / Inventory
بوفه مالک فروش سریع، کاتالوگ کالا، موجودی، ورود/خرید، اصلاح، ضایعات، برگشت، حداقل موجودی و هشدار کمبود است. نسخه اول یک انبار اصلی دارد ولی مدل برای Stock Location آینده آماده می‌شود.

## جایگاه مرکز مدیریت فعلی

OperationsPage تا پایان Stage 1B یک QA/Backoffice Hub موقت است. علت نگه‌داشتنش این است که قابلیت‌های تازه‌ساخته‌شده هنوز باید بدون پراکندگی تست شوند.

بعد از انتقال هر قابلیت به صفحه مالک:
1. رفتار آن قابلیت با همان MockService حفظ می‌شود.
2. تست‌های UI/رفتاری انجام می‌شود.
3. تب متناظر از OperationsPage حذف می‌شود.
4. وقتی همه تب‌ها منتقل شدند، OperationsPage حذف می‌شود.

## قانون اتصال به API

تمام صفحات باید API را از طریق Serviceهای دامنه‌ای مصرف کنند؛ هیچ صفحه‌ای نباید مستقیم به SQLite یا دیتابیس دسترسی داشته باشد.

قرارداد هر Service با DTO فعلی MockService ثابت می‌ماند تا در Stage 2 فقط منبع داده از Mock به API تغییر کند.

## نقش‌ها

- Operator: عملیات جاری، مشتری، بوفه، جلسه و گزارش شیفت خودش طبق Permission.
- Manager: مدیریت مالی، تعرفه، مشتری، بوفه و گزارش‌ها طبق Permission.
- Owner: کنترل کامل، تنظیمات امنیتی، کاربران و Recovery.

UI می‌تواند قابلیت بدون مجوز را پنهان کند؛ اما کنترل واقعی Permission باید در Server نیز اجباری باشد.

## قانون عدم بازطراحی

این سند مجوز تغییر ظاهر Prototype نیست. جای قابلیت‌ها ممکن است تغییر کند، اما Component، رنگ، RTL، رفتار اصلی، میانبرها و ساختار بصری تأییدشده باید حفظ شوند.
