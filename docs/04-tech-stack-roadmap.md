## ۱) محصول‌های مشابه با چه تکنولوژی‌ای ساخته شده‌اند؟ (اعتبارسنجی واقعی)

| محصول | نشانه‌ی فنی | نتیجه برای ما |
|---|---|---|
| **بازی‌نت (ایرانی)** | پیش‌نیاز نصب: **WebView2 Runtime** | UI آن با تکنولوژی وب داخل پوسته ویندوزی است → الگوی «UI وب + هسته محلی» در ایران جواب داده |
| **Smartlaunch** | ویندوزی on-premise، نسل کلاسیک .NET/Win32 | مدل سرور محلی + کلاینت ویندوزی سال‌ها در مقیاس جهانی کار کرده |
| **SENET (E-launcher)** | کلاینت شل ویندوزی + پلتفرم ابری | کلاینت شل استاندارد صنعت است |
| **LaunchDesk** | تنظیمات DNS/IP، CCBOOT/PXE در کلاینت | کلاینت به‌صورت سرویس سیستم‌عامل کار می‌کند، نه یک برنامه معمولی |
| **گیم‌لود / گیم کانکت** | Server/Client ویندوزی، بروزرسانی آفلاین کلاینت | کلاینت باید مکانیزم آپدیت از سرور داشته باشد |

**جمع‌بندی اعتبارسنجی:** هیچ‌کدام Flutter/Cross-platform موبایلی نیستند؛ همه یا ویندوز نیتیو هستند یا وب داخل پوسته. مسیر پیشنهادی ما (سرور .NET + داشبورد وب + کلاینت ویندوزی) دقیقاً هم‌راستا با صنعت است.

## ۲) مقایسه‌ی استک‌های ممکن برای سرور + داشبورد

| گزینه | مزایا | معایب | امتیاز برای این پروژه |
|---|---|---|---|
| **C# / .NET (ASP.NET Core) + React + SQLite** ⭐ | یک زبان برای سرور و کلاینت؛ SignalR داخلی برای realtime؛ اکوسیستم ویندوز قوی؛ EF Core برای SQLite؛ LTS مشخص؛ درایورهای سخت‌افزاری (چاپگر، WoL) راحت | دو فریم‌ورک فرانت و بک | **۱۰/۱۰** |
| Node.js + React + SQLite | یک زبان (JS) در همه‌جا؛ اکوسیستم وب بزرگ | کلاینت قفل‌کننده‌ی ویندوز با Node سخت و ناپایدار است؛ سرویس ویندوزی ضعیف | ۶/۱۰ |
| Tauri/Rust یا Electron + وب | UI وب خالص | برای قفل شل ویندوز و سرویس سیستمی مناسب نیست؛ حجم/پیچیدگی؛ دو استک جدا برای کلاینت | ۴/۱۰ |
| WPF خالص بدون وب (همه‌چیز دسکتاپ) | تک‌تکنولوژی، آفلاین کامل | چند صندوقه و تبلت نمی‌شود؛ RTL و گرید بزرگ در WPF کندتر توسعه می‌رود؛ آپدیت UI سخت | ۵/۱۰ |
| Flutter Desktop | یک کدبیس موبایل+دسکتاپ | اکوسیستم دسکتاپ ویندوز جوان؛ سرویس/شل ویندوز ضعیف | ۴/۱۰ |

**تصمیم نهایی پیشنهادی:**
- **سرور:** ASP.NET Core 10 (LTS) — Web API + **SignalR** برای تایمر زنده و فرمان به کلاینت‌ها
- **دیتابیس:** SQLite با EF Core (+ snapshot خودکار روزانه؛ مسیر ارتقا به PostgreSQL باز می‌ماند)
- **داشبورد:** React + TypeScript، فارسی/RTL با `dir="rtl"`، نمودارها با Recharts، تقویم شمسی با کتابخانه‌ی استاندارد (Luxon + shamsi یا react-multi-date-picker)
- **کلاینت PC (فاز ۳):** WPF (.NET) برای UI مشتری + **Worker Service ویندوزی** برای Heartbeat/فرمان‌ها؛ قفل از طریق **Shell Launcher / رجیستری AlternativeShell** روی یوزر محدود Kiosk (روش استاندارد مایکروسافت — کیوسک رسمی ویندوز) + سیاست‌های گروهی (GPO) برای بستن Task Manager و CMD
- **نصب/آپدیت:** Inno Setup برای نصب سرور؛ آپدیت کلاینت از سرور (الگوی گیم‌لود/گیم کانکت)؛ لاگ با Serilog

### قواعد طلایی کدنویسی از روز اول
1. **پول:** همه‌جا `long` به‌صورت تومان (بدون اعشار) یا `decimal` — هرگز float/double
2. **تاریخ:** در دیتابیس UTC/میلادی ذخیره، در UI شمسی — تبدیل فقط در یک لایه‌ی مرکزی
3. **موتور محاسبه هزینه:** توابع خالص (Pure Function) جدا از UI و دیتابیس → قابل تست واحد ۱۰۰٪ (مهم‌ترین بخش مالی برنامه)
4. **هر تغییر دیتابیس با Migration** — نه دست‌کاری دستی
5. **لاگ ساختاریافته** (Serilog) از روز اول + `Try/Catch` در نقاط حساس با ثبت جزئیات

## ۳) مسیر شروع کار (قدم‌به‌قدم، سفارش دقیق)

### مرحله ۰ — زیرساخت (۱ روز)
- ساخت سولوشن .NET + پروژه‌ی React (یک ریپو، دو پوشه: `server/` و `dashboard/`)
- اتصال SQLite + اولین Migration + سیستم لاگ
- اسکلت SignalR (هاب `Hub` سرور + اتصال تست از React)

### مرحله ۱ — مدل داده و داده‌های پایه (۲–۳ روز)
- اسکیمای کامل: Station, StationType, Tariff, Session, Invoice, InvoiceItem, Customer, WalletTransaction, Shift, Expense, AppUser, AuditLog
- CRUD ایستگاه‌ها و تعرفه‌ها در داشبورد + ورود/کاربران (مدیر/اپراتور)
- **خروجی قابل نمایش:** می‌توانی ۶۱ ایستگاه و تعرفه‌هایش را تعریف کنی

### مرحله ۲ — هسته‌ی تایمر و جلسه (۱ هفته) ⭐ مهم‌ترین مرحله
- موتور جلسه در سرور: Start/Stop/Extend/Transfer + محاسبه‌ی لحظه‌ای هزینه با تعرفه‌ی ساعتی/نفره‌ای/بازه‌ای
- SignalR: تایمر زنده روی گرید داشبورد + رنگ وضعیت‌ها
- هشدار صوتی پایان وقت + بازیابی جلسات باز بعد از ری‌استارت سرور (قطع برق)
- **تست واحد موتور محاسبه** (تعرفه عوض شود وسط جلسه؟ عبور از دو بازه‌ی ساعتی؟)
- **خروجی:** برنامه در عمل برای کنسول‌ها و فوتبال‌دستی‌ها قابل استفاده است!

### مرحله ۳ — تسویه و فاکتور (۳–۴ روز)
- فاکتور ترکیبی (زمان + آیتم دستی)، تخفیف، رند، پرداخت نقد/کارت، بستن جلسه
- گزارش روزانه ساده + تفکیک نقد/کارت
- **خروجی:** چرخه‌ی کامل «شروع → بازی → تسویه» کار می‌کند = **MVP قابل استفاده در گیم‌نت واقعی**

### مرحله ۴ — بوفه، مشتریان، کیف پول (۱ هفته)
- کالا/دسته‌بندی/موجودی + فروش روی جلسه یا مستقل
- مشتری + جست‌وجو + کیف پول + بدهی/بستانکاری
- گزارش‌های نموداری ماهانه/سالانه + ثبت هزینه + سود خالص + بستن شیفت

### مرحله ۵ — کلاینت PC (۱.۵–۲ هفته)
- سرویس ویندوزی: Heartbeat + دریافت فرمان (قفل/باز/ری‌استارت/پیام) + ارسال وضعیت
- WPF شل: صفحه‌ی لاگین/انتظار، نمایش زمان باقیمانده، هشدار صوتی، لیست بازی‌ها
- قفل: یوزر Kiosk محدود + Shell Launcher + GPO (بستن Task Manager/CMD)
- نصب و آپدیت خودکار کلاینت از سرور
- **نکته‌ی اجرایی:** اول روی **۲–۳ کیس آزمایشی** در گیم‌نت خودت؛ نه یک‌باره روی ۴۰ کیس

### مرحله ۶ — صیقل و مقاوم‌سازی (مستمر)
- بکاپ خودکار + تست بازگردانی، Audit Log کامل، رفع باگ‌های واقعی از استفاده‌ی روزمره
- نصب نهایی روی همه‌ی کیس‌ها

### مرحله ۷ — امکانات تمایز (بعد از پایداری)
- رزرو/خط انتظار، تورنمنت، پیامک، چاپ حرارتی، اپ موبایل مدیر

## ۴) بهترین مدل پیشروی (روش کار)

### ۴.۱) معماری کد: Vertical Slice
به‌جای لایه‌بندی کلاسیک (همه‌ی مدل‌ها → همه‌ی سرویس‌ها → همه‌ی UI)، هر فیچر را **عمودی کامل** بساز: از دیتابیس تا API تا UI در یک پوشه (مثلاً `Features/Sessions/`). 
- هر اسلایس خودش قابل تحویل و تست است
- برای پروژه‌ی تک‌نفره/کوچک، این سریع‌ترین مدل با کمترین اتلاف است (الگوی رایج .NET مدرن)

### ۴.۲) اصل «هر هفته یک نسخه‌ی قابل اجرا»
- پایان هر هفته، برنامه باید **اجرا شود و کاری انجام دهد** — حتی کوچک
- دمو برای خودت: یک سناریوی واقعی گیم‌نت را با آن انجام بده (مثلاً یک جلسه‌ی PS5 کامل)

### ۴.۳) استفاده‌ی موازی زودهنگام (Parallel Run) ⭐
بعد از مرحله ۳، برنامه را **هم‌زمان با روال فعلی** در گیم‌نت خودت استفاده کن:
- اپراتور همان کار قبلی را می‌کند + در برنامه ثبت می‌کند
- باگ‌های واقعی (که در آزمایشگاه پیدا نمی‌شوند) بیرون می‌ریزند
- اعتماد اپراتورها قبل از وابسته شدن کامل ساخته می‌شود

### ۴.۴) اولویت‌بندی با ارزش مالی
هر فیچر را با این سوال انتخاب کن: «آیا امروز در گیم‌نت پول یا وقت صرفه‌جویی می‌کند؟»
- تایمر/فاکتور = پول مستقیم → اول
- تورنمنت = جذب مشتری → بعداً
- تم و گرافیک فانتزی → آخر

### ۴.۵) کنترل کیفیت
- **تست واحد فقط برای موتور هزینه و کیف پول** (جاهایی که خطا = ضرر مالی)؛ UI را با تست دستی سناریوها
- Git: کامیت‌های کوچک روزانه + برچسب نسخه (v0.1، v0.2...) تا هر وقت خواستی به نسخه‌ی سالم برگردی
- دیتابیس واقعی گیم‌نت هرگز با نسخه‌ی نیمه‌کاره لمس نشود (نسخه‌ی dev با داده‌ی ساختگی جدا باشد)

### ۴.۶) الگوی خطری که باید از روز اول مدیریت شود
| ریسک | پادزهر در طراحی |
|---|---|
| قطع برق وسط جلسه | جلسه در دیتابیس Active است؛ استارت سرور = بازیابی + محاسبه‌ی زمان قطعی |
| هک/دور زدن کلاینت توسط مشتری | سرور مرجع است؛ کلاینت فقط نمایش/فرمان؛ Heartbeat قطع → هشدار به اپراتور |
| خطای انسانی اپراتور | لاگ کامل + تأیید دو مرحله‌ای برای حذف/تخفیف بزرگ |
| گم شدن داده‌ها | بکاپ روزانه خودکار + نگهداری ۳۰ نسخه + تست بازگردانی ماهانه |
| کسری اعشار در پول | long تومان + توابع خالص تست‌شده |

## ۵) جمع‌بندی یک‌پاراگرافی
با **ASP.NET Core + SignalR + SQLite + React (RTL)** سرور و داشبورد را بساز؛ موتور هزینه را **توابع خالص با تست واحد** طراحی کن؛ **Vertical Slice** پیش برو و هر هفته نسخه‌ی اجرایی داشته باش؛ بعد از مرحله‌ی تسویه، برنامه را **موازی با روال فعلی گیم‌نت** به کار بگیر تا باگ‌های واقعی بیرون بیاید؛ کلاینت قفل‌کننده را با **WPF + سرویس ویندوزی + Shell Launcher** در فاز جدا و اول روی ۲–۳ کیس آزمایشی اجرا کن.
